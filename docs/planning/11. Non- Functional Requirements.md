## Non-Functional Requirements

Non-functional requirements define **how well the system should work**, rather than what functions it provides. They are important because this project is intended to be both a college major project and a professional resume project.

### NFR-01 — Performance

The system should provide fast responses for normal operations such as:

- Login
- Project retrieval
- Task creation
- Resource assignment
- Dashboard loading
- Schedule calculation

For normal requests, the target response time should generally be **under 2 seconds**, excluding heavy reports or complex optimization operations.

### NFR-02 — Scalability

The architecture should allow the system to grow as the number of:

- Users
- Projects
- Tasks
- Workers
- Vendors
- Resources

increases without requiring a complete redesign.

### NFR-03 — Reliability

The system should operate consistently and should minimize failures during normal usage.

Important operations such as project updates, task assignments, and schedule modifications should be handled reliably.

### NFR-04 — Data Integrity

The system must maintain accurate and consistent project data.

For example:

- A task should not reference a nonexistent project.
- A dependency should not reference a nonexistent task.
- Invalid circular dependencies should be prevented.
- Resource assignments should follow defined constraints.
- Important database operations should use transactions where required.

### NFR-05 — Security

The system must protect user and business data through:

- Secure authentication
- Password hashing
- JWT-based authentication
- Role-based authorization
- Input validation
- Secure API endpoints
- Protection against unauthorized access
- Proper database access controls

### NFR-06 — Availability

The system should be available whenever authorized users need to access project information and should recover gracefully from temporary failures.

### NFR-07 — Usability

The interface should be:

- Simple
- Consistent
- Responsive
- Easy to navigate
- Understandable for non-technical business users

A Project Manager should be able to understand the status of a project without needing technical knowledge.

### NFR-08 — Maintainability

The source code should be organized into logical modules with clear separation between:

```
Controller
   ↓
Service
   ↓
Repository
   ↓
Database
```

The frontend and backend should also remain clearly separated.

### NFR-09 — Extensibility

The system should be designed so that future modules can be added without major changes to the existing system.

Potential future additions include:

- AI/ML
- Schedule optimization
- Mobile application
- Advanced analytics
- External integrations
- Email/SMS notifications

### NFR-10 — Compatibility

The web application should work correctly on commonly used modern browsers such as:

- Google Chrome
- Microsoft Edge
- Mozilla Firefox

### NFR-11 — Responsive Design

The interface should adapt to:

- Desktop
- Laptop
- Tablet

The primary target will be desktop/laptop users because project management involves dashboards, Gantt charts, and scheduling interfaces.

### NFR-12 — Auditability

Important changes should be traceable.

The system should record:

- Who performed the action
- What was changed
- When it was changed
- Which project/task/resource was affected

### NFR-13 — Backup & Recovery

Project and user data should be capable of being backed up and restored to reduce the impact of data loss or system failure.

### NFR-14 — Testability

The system should be designed so individual components can be tested independently.

Testing should cover:

- Backend services
- REST APIs
- Scheduling algorithms
- Dependency calculations
- Database operations
- Frontend components
- End-to-end workflows

### NFR-15 — Deployment

The application should be deployable using **Docker** so that the development and production environments remain consistent.

### NFR-16 — Observability

The system should maintain appropriate application logs for:

- Errors
- Authentication events
- Important business operations
- Scheduling failures
- Unexpected system behavior

This will make debugging and maintenance easier.

### NFR-17 — Accuracy of Scheduling

The scheduling engine must respect defined constraints such as:

- Task dependencies
- Resource availability
- Task duration
- Working periods
- Project deadlines

The system should never knowingly generate a schedule that violates mandatory dependencies or resource constraints.

### NFR-18 — Explainability

Important scheduling decisions should be understandable to the Project Manager.

For example, instead of simply saying:

> **Project At Risk**

the system should explain:

> **Project At Risk because Vendor A is delayed by 3 days, affecting Tasks 12, 15, and 18 on the critical path.**

This requirement will become particularly important when we introduce the intelligent/AI layer.

### NFR-19 — Human Control

The system should not automatically make critical business decisions without authorization.

For advanced recommendations:

```
System Analysis
      ↓
Recommendation
      ↓
Manager Review
      ↓
Approve / Reject
      ↓
System Action
```

This will form the foundation for our future **Human-in-the-Loop AI** design.

### NFR-20 — Cost Efficiency

The initial system should rely primarily on open-source technologies and avoid unnecessary infrastructure or third-party services so that the project can be developed and demonstrated with minimal cost.

This keeps our architecture intentionally lean:

**React + TypeScript → Spring Boot + Java → PostgreSQL → Docker**

with additional AI/optimization components introduced only when they provide a clear benefit.
