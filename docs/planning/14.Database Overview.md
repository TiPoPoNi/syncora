## Database Overview

The system will use **PostgreSQL** as its primary relational database. The database will store all persistent information related to users, projects, tasks, resources, scheduling, dependencies, vendors, workers, clients, notifications, and audit records.

The database will be designed around the relationships between **projects, tasks, resources, and schedules**, because these relationships form the foundation of the scheduling system.

### 1. Main Entities

The initial database will contain the following major entities:

```
User
Role
Client
Project
Project_Member
Task
Task_Dependency
Worker
Skill
Worker_Skill
Vendor
Resource
Resource_Assignment
Task_Assignment
Milestone
Schedule
Notification
Audit_Log
```

### 2. High-Level Relationship

```
                    USER
                     │
             ┌───────┼────────┐
             ▼       ▼        ▼
          CLIENT   WORKER   VENDOR
             │       │        │
             │       │        │
             └───────┼────────┘
                     │
                     ▼
                  PROJECT
                     │
          ┌──────────┼───────────┐
          ▼          ▼           ▼
        TASK      MILESTONE   RESOURCE
          │
          ▼
   TASK_DEPENDENCY
          │
          ▼
    TASK_ASSIGNMENT
          │
          ▼
       SCHEDULE
```

This is a conceptual model. The exact database schema will be finalized during the detailed database-design phase.

### 3. User & Role Data

The `User` entity will store common authentication and account information.

Examples:

- User ID
- Name
- Email
- Password hash
- Role
- Account status
- Created date
- Updated date

Roles will determine what operations each user is allowed to perform.

### 4. Client Data

The `Client` entity will store:

- Client ID
- Client name
- Contact information
- Organization
- Requirements
- Account status

A client can have multiple projects.

```
Client
   │
   ├── Project A
   ├── Project B
   └── Project C
```

### 5. Project Data

A project will contain information such as:

- Project ID
- Project name
- Client ID
- Project manager
- Description
- Start date
- Deadline
- Priority
- Status
- Progress
- Budget (if implemented)
- Created/updated timestamps

A project can contain many tasks and milestones.

### 6. Task Data

Tasks are one of the most important entities.

A task may contain:

- Task ID
- Project ID
- Task name
- Description
- Duration
- Planned start date
- Planned end date
- Actual start date
- Actual completion date
- Priority
- Status
- Progress
- Required skill/resource
- Created/updated timestamps

### 7. Task Dependencies

Task dependencies will be stored separately because one task can depend on another.

Example:

```
Task A ──────→ Task B
                │
                ▼
              Task C
```

A `Task_Dependency` relationship can represent:

```
Predecessor Task → Successor Task
```

This relationship will later be used by the scheduling engine and Critical Path Method.

### 8. Worker & Skill Data

Workers will have:

- Worker ID
- User ID
- Skills
- Experience
- Availability
- Working hours
- Current workload

Skills should be separated into their own entities so one worker can have multiple skills.

```
Worker
   │
   ├── Java
   ├── SQL
   └── Project Management
```

### 9. Vendor Data

Vendor information may include:

- Vendor ID
- Vendor name
- Contact information
- Services/materials
- Availability
- Performance information
- Status

Vendors can be associated with projects and tasks.

### 10. Resource Data

Resources can represent:

- Workers
- Equipment
- Materials
- External services
- Other assignable project resources

Each resource can have:

- Availability
- Capacity
- Type
- Status
- Cost information where applicable

### 11. Assignment Data

Assignment tables will connect resources with tasks.

For example:

```
Worker B
    ↓
Task 17
    ↓
Project Alpha
```

The assignment data can store:

- Resource ID
- Task ID
- Start date
- End date
- Allocation percentage
- Assignment status

This information is essential for detecting resource conflicts.

### 12. Schedule Data

The schedule will contain the calculated/planned timing information.

It may store:

- Task ID
- Planned start
- Planned finish
- Actual start
- Actual finish
- Duration
- Slack
- Critical-path status
- Schedule version

This allows the system to compare the original plan with the current schedule.

### 13. Milestone Data

Milestones will represent important project checkpoints.

Examples:

```
Design Complete
       ↓
Material Received
       ↓
Production Complete
       ↓
Installation Complete
       ↓
Final Delivery
```

Each milestone can have:

- Name
- Project
- Deadline
- Status
- Approval status

### 14. Notification Data

The database will store important notifications such as:

- Task assignments
- Deadline reminders
- Resource conflicts
- Vendor delays
- Project risks
- Approval requests

### 15. Audit Log

The `Audit_Log` entity will record important system activities.

For example:

```
User: Manager
Action: Updated Task Deadline
Task: T-104
Old Date: 20 Oct
New Date: 23 Oct
Timestamp: ...
```

This provides accountability and helps with debugging.

### 16. Database Design Principles

The database will follow:

- Relational data modeling
- Primary and foreign keys
- Referential integrity
- Appropriate normalization
- Unique constraints
- Check constraints
- Indexing for frequently queried data
- Transactions for critical operations

We will avoid duplicating information unnecessarily.

### 17. Important Database Relationship

The most important relationship in the entire project will eventually look conceptually like:

```
PROJECT
   │
   ├────────────── TASK
   │                 │
   │                 ├──── DEPENDENCY
   │                 │
   │                 └──── ASSIGNMENT
   │                           │
   │                           └──── RESOURCE
   │
   ├────────────── MILESTONE
   │
   └────────────── SCHEDULE
```

This structure gives the scheduling engine the information it needs to answer questions such as:

> Which tasks depend on this task?

> Which worker is assigned?

> Is that worker available?

> What happens if this task is delayed?

> Does the delay affect the critical path?

> Will the project still meet the client's deadline?

The **exact ER diagram, table definitions, columns, keys, indexes, and normalization strategy** should be designed as a separate step after this basic documentation. That way, we don't prematurely lock ourselves into a database structure before finalizing the scheduling logic.
